# Player scenarios and mobile playtests

## Check the layout before art

For a new screen or flow, capture four things in the recipe draft: **goal**, **entry**, **primary action**, and **observable success**. For example, a player enters a drill while the relay is under attack, taps Shield, and sees the projectile disappear while health stays steady and a short “Shot deflected” message confirms the outcome. Identify the gameplay state or event that supplies the signal.

Build a simple wireframe with text, blocks, actual hit areas and a gameplay frame when available. Use an existing approved layout as the starting point. Keep the primary action recognizable and protect the gameplay the player needs to see. For a HUD, list persistent information, contextual controls, and the conditions that show or hide each. Inspect at least a representative frame and a busy frame on the compact profile. Note where the thumb rests, what it covers, and which actions need to work at the same time. Use a representative fixture and label it when the project cannot supply gameplay yet.

## Observe a first attempt

Give a player unfamiliar with the screen a goal that does not name the control or spell out the route. For the shield drill, start in independent practice and say “Keep the relay safe from the next incoming shot.” Ask what happened after the attempt. Count success when the player performs the action and identifies its result from the UI. Note the first action, misses or wrong taps, requests for help, how the player recognized the outcome, and any issue that prevented completion. Keep observations tied to the exact profile, device and build tested.

When a participant or physical phone is unavailable, exercise the same path in the browser and record the result as a functional check. Leave first-attempt comprehension and physical reach pending. For platform, localization and accessibility evidence, use [the handoff QA report](handoff.md#mobile-qa-report).
