# UI handoff

## Files and status

Place the pack manifest at `asset-pack.json`, and each screen in its own directory with `recipe.md`, `recipe.json`, and a `preview.png` or explicitly named viewport/state captures. Use paths relative to the handoff or an explicitly declared project asset root. Deliver a [screen map](screen-map.md) as `screen-map.md` for whole games and large catalogs. Keep rejected concepts and intermediate generation files outside the runtime asset manifest. An approved pack can be extended with a new version while existing references remain resolvable.

The caller receives the status (`ready`, `awaiting-style-selection`, or `blocked`), artifact paths, the supported states and profiles, instructions to bind the data/actions and play the motion, and concrete gaps. Use `ready` after checking the real layered PNG, mandatory assets, and an interactive preview of the relevant motion and player states. Use `blocked` with a precise missing input and the partial recipe when progress can continue independently.

## JSON fields

| File | Required fields |
| --- | --- |
| Asset pack | `id`, `version`, `assets`. Every asset entry has a stable ID (the key), `path`, `size` [width, height] for images, and `fit`. Options include `contain`, `cover`, `stretch`, and `slice`. A sliced asset includes `slice` for source pixels and `border` for logical destination units, both [top, right, bottom, left]. A font uses `fit: "font"` and includes its license when supplied. Pack provenance identifies the source or approved concept. |
| Screen | `id`, `pack` [ID and version at the top level of the pack reference], `design` (logical width, viewport profiles and safe insets), `data`, `actions`, `states`, `initialState`, `nodes`, and `motion`. Declare an empty array or object for a category with no entries. |
| Node | Stable `id`, logical `box` [x, y, width, height] and optional `boxes` overrides keyed by viewport profile. Siblings are listed back to front and children are relative to the parent. Root coordinates use the safe area unless `space: "screen"` is set. A node may reference an `asset`, a data-bound `text`, an `action`, state visibility, and other declared layout or typography properties. Implement touch areas separately where the visible art is small. |
| Motion | Named sequences with triggering action or state, duration in milliseconds, ordered visual phases, and tracks. A track names a node and property, and gives relative keyframes with values, times, and easing. Include skip target, replay/duplicate-input behavior, cancellation, and a reduced-motion result. Include sound/haptic events when they belong to the design and label missing sources explicitly. |

The recipe is the authority for layout, visual states, and timing. Expose actual text and values as data, with example fixtures for visually significant states. Set optional `locale` to the language tag of the preview content. Describe how to map the target game's authoritative state and commands, including asynchronous, unavailable, or expired states where applicable. The handoff uses logical units and asset IDs. Native UI node names and import settings are decisions for the receiving project.

Each profile declares `viewport` [width, height] and `safeInsets` [top, right, bottom, left] in that viewport's pixels. Convert insets to the logical coordinate system by scaling with the ratio of logical width to viewport width. A keyframe in the pilot has form `[timeMs, value, easing]` and uses the destination keyframe's easing for interpolation. Use `keysByProfile` to override a path when the source and destination move between viewport profiles.

## Visibility and routes

- For new recipes, add `motionDefaults` with `enter: { "ms": 160, "y": 8 }` and `exit: { "ms": 120, "y": -6 }`. Enter fades from zero and settles from the specified offset. Exit fades to zero and moves toward its offset. Both use cubic ease-out. A changing parent moves its group together. Authored tracks own visibility for the nodes they animate. Use `visibilityMotion: "instant"` for an immediate signal or layer. For reduced motion, settle the visual state immediately while preserving the outcome.
- For a connected preview, declare optional `screens` keyed by ID with an `initial` state for each screen. A state declares its `screen`, and a root node declares its `screen` when it belongs to one view. Roots without a screen are shared. An input action declares allowed `from` states and `navigate: { to, label, focus }` with the destination screen and focus node. Add `back: true` to flag a return. Remember the last state of each visited screen and restore the originating control on return. An event can update a remembered state with `remember: { screenId: stateId }`.
- A top-level switch uses `navigate.section: true` to open the destination's initial state and clear the detail route history. Set `currentIn` on its input node to the states where the section is current, including its details. The preview marks it visually and with `aria-current="page"`. A screen-owned list container can use `scroll: "vertical"` to retain its scroll offset when the player follows a route or returns. Keep persistent controls outside the list.
- Play a 260 ms directional transition with a 28-unit horizontal offset and cubic ease-out. Fade the source over the first 110 ms and bring in the destination from 45 ms to the end. The leaving screen becomes inert immediately. Enable the new screen and restore focus when the move settles. A screen action is available in the timeline inspector under its action ID. Seeking into the action samples two screen layers with input disabled and no game events.
- For a localized effect, record an optional `impacts` entry in the sequence with `event`, `target`, `effect`, peak time `at`, and decay end `end`. The target is the node that changes. The effect is the node that supplies the feedback. Use the same timeline frame for the visible change and its peak. When a predicted value travels, align both text boxes so it meets the current value's anchor before the handoff. Start the result sequence when the operation is confirmed. Reduced motion settles to that confirmed result immediately.

## Ambient motion and progress

- Optional `loops` are keyed by ID. A loop declares a `label`, eligible `states`, full `period` in milliseconds including rest, and decorative `tracks` using the normal keyframe format. An optional `control` names the input node that must be available. List the preferred inspection state first. Only visible eligible layers run. A foreground action, modal, route, hidden document, or reduced-motion preference suppresses the loop. The timeline inspector samples a single cycle without sending an action.
- A progress state can supply `progress.value` from 0 to 100 or leave the value absent when unknown. A progress node names its clipped child in `progress.fill` and exposes the same value to assistive technology. A text node with `text: { "progress": true }` shows the percentage when present. Clip the shine inside the fill and allow its clock to run while measured progress is held. Use a separate indeterminate band for unknown progress. Keep paused and complete states static and readable.
- The preview can expose a `previewDemos` entry with `label`, starting `state`, and optional `motion` for scripted progress. Such a sequence can set `allowLoops: true` to run an activity indication while it applies preview-only states. It has no trigger or gameplay events. Use `reduced: "play"` for real or simulated state updates that must still occur while visual loops are suppressed.

Record a QA pass with a real rendered frame. Test both supported extremes of viewport and safe insets, long localized text where applicable, larger numbers, and legibility over art or gameplay. Inspect input capture on modal open, Skip and Back behavior, interrupted transitions, and final focus. Triggering an animation should never grant a reward twice. Stepping through frames should never dispatch an action.

## Mobile QA report

In `recipe.md`, record the scenario, profile or device, build or browser, and evidence. Mark each applicable check as passed, failed, or pending. Link rendered frames and include the steps and observed result for interactive checks. Use the [player scenario and playtest guide](mobile-ux.md) for a first-attempt task.

| Check | Evidence to capture |
| --- | --- |
| Touch targets and reach | Measure both dimensions of the actual hit area. Use 44 × 44 pt for frequent iOS game controls and 48 × 48 dp on Android as platform targets. Verify the game's logical-to-native mapping in a native build. Exercise edge gestures, adjacent buttons, and simultaneous input where relevant with the intended grip. |
| Gameplay readability | Check important HUD text, icons and focus in light, dark and busy frames. Record the background or contrast measurement for critical labels. Give important status changes a text or shape cue in addition to color. With reduced motion or sound off, check that the result remains perceivable. |
| Localization | Render long localized or expanded strings and large values on the narrowest supported profile. Check glyph coverage, wrapping and the agreed minimum text size. For right-to-left locales, check reading order, mixed text and numbers, and direction-dependent controls. |
| Browser and device scope | Label desktop browser, browser touch emulation, mobile browser on a named device, or native build on a named device. Leave physical reach, actual OS gesture interaction, and native scaling pending until observed where applicable. |
